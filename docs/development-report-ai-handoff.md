# 개발보고서 AI 작업 인계 가이드

## 준비된 기준 파일

보고서 작업 전에 다음 파일을 함께 사용한다.

1. `/Users/junho2026/Downloads/해운물류 개발보고서.pdf` — 주최 측이 제공한 공식 11쪽 양식
2. `docs/development-report-template-map.md` — 공식 PDF의 항목명·순서·작성 지시를 옮긴 텍스트 기준
3. `docs/notion-project-context.md` — Notion 전체 내용과 사용자 확인 사항을 통합한 사실 기준
4. `docs/hardware-configuration-history.md` — 현재 센서 구성과 취소된 초기 프로토타입 구분
5. `.cursor/rules/rail-deformation-context.mdc` — 용어와 구현 문맥 규칙

제출 양식의 기준은 Markdown 초안이 아니라 공식 PDF다. Markdown 파일에서는 PDF의 항목별로 들어갈 글·표·사진 설명을 작성하고, 사용자가 ChatGPT를 이용해 공식 양식에 이식한다.

## 다른 Cursor 채팅에서 사용할 프롬프트

아래 내용을 새 채팅에 그대로 입력한다.

```text
@docs/development-report-template-map.md
@docs/notion-project-context.md
@docs/hardware-configuration-history.md
@.cursor/rules/rail-deformation-context.mdc

공식 개발보고서 PDF는 /Users/junho2026/Downloads/해운물류 개발보고서.pdf 이고, PDF의 정확한 항목과 작성 지시는 development-report-template-map.md에 정리되어 있어.
위 파일을 먼저 전부 읽고 공식 PDF 각 칸에 이식할 개발보고서 원고를 작성해줘.

작업 원칙:
1. development-report-template-map.md의 공식 항목명과 순서를 변경·삭제하지 않는다.
2. 작품 개요와 작품 구성도는 각각 공식 양식 1쪽 분량에 맞게 작성한다.
3. Markdown 초안은 제출 양식 자체가 아니라 PDF에 넣을 항목별 삽입 원고다. 공식 표의 열과 작성 지시를 유지한다.
4. 프로젝트의 핵심 대상은 하부 주행 레일의 단차·국부 침하·뒤틀림이다.
5. 현재 센서 구성은 ESP32-C3 Mini + MPU-6050 + ADS1115 + GTRIC LR18-08U M18 아날로그 유도형 근접 센서다. 실제 몸체 라벨로 DC 15–30V 동작, 0–10V 출력, 1–8mm 감지 거리를 확인했고, 실물 사진으로 ADS1115용 분압·보호 회로를 포함한 센서 모듈 배선 상태를 확인했다. 2026-08-23 사용자 확인 기준으로 ESP32-C3 펌웨어 동작, 구동부 출력과 전체 모형 조립은 완료되었고 회로값·측정전압·반복 주행·실측 저장은 검증 필요 상태다.
6. ESP32-S3 + ADXL345 + HC-SR04는 취소된 초기 프로토타입이므로 현재 구성이나 최종 성과로 쓰지 않는다. 필요한 경우에만 과거 개발 이력으로 구분해 적는다.
7. 구동부 3D 출력 외피 안에 현재 센서 모듈을 수납하는 구조를 반영한다.
8. 합성 데이터·더미 시연 결과와 실제 계측 결과를 구분한다.
9. 완료, 진행 중, 계획, 검증 필요 상태를 근거에 맞게 구분하고 확인되지 않은 수치나 성과를 만들지 않는다.
10. 원시 센서값을 AI에 바로 넣는다고 쓰지 말고 웨이블릿 디노이징, 파고율 등 특징 공학을 거친다고 설명한다.
11. 구매한 상용 3D 모델과 물리 제작용 평판·구동부 모델을 구분한다.
12. 공식 양식과 최신 문맥이 충돌하는 내용을 먼저 보고한 뒤, 공식 항목별 원고를 작성한다.

지금은 먼저 충돌 항목과 수정 계획을 짧게 제시하고, 그다음 공식 PDF 항목별 삽입 원고를 작성해줘. 작성 후에는 [확인 필요] 항목, 필요한 사진·표·구성도 목록, PDF에 이식할 때의 페이지별 분량 주의사항도 알려줘.
```

특정 항목만 작성할 때는 마지막 문단을 다음처럼 바꾼다.

```text
이번에는 공식 개발보고서의 "[작성할 항목명]" 칸에 넣을 원고만 작성해줘. development-report-template-map.md의 해당 항목 작성 지시와 분량을 지키고 다른 항목은 수정하지 마. 작성한 문장마다 통합 문맥에서 근거를 확인하고, 근거가 부족한 내용은 [확인 필요]로 표시해줘.
```

## ChatGPT에서 사용할 프롬프트

ChatGPT에는 다음 파일 5개를 업로드한다.

- `/Users/junho2026/Downloads/해운물류 개발보고서.pdf`
- `docs/development-report-template-map.md`
- `docs/notion-project-context.md`
- `docs/hardware-configuration-history.md`

업로드 후 아래 프롬프트를 입력한다.

```text
첨부한 공식 PDF와 기준 문서들을 근거로 스마트해운물류 개발보고서에 이식할 최종 원고를 작성해줘.

- 제출 양식은 첨부한 "해운물류 개발보고서.pdf"가 유일한 기준이다.
- "공식 양식 항목표"의 항목명, 순서, 표 구조와 작성 지시를 그대로 유지한다.
- 공식 양식에 없는 독자 목차를 만들지 않는다.
- 작품 개요와 작품 구성도는 각각 반드시 1쪽 분량으로 구성한다.
- "프로젝트 통합 문맥"을 최신 사실의 기준으로 사용한다.
- "하드웨어 구성 변경 이력"에 따라 현재 구성과 과거 프로토타입을 엄격히 구분한다.
- 핵심 대상은 하부 주행 레일의 단차·국부 침하·뒤틀림이다.
- 현재 하드웨어는 ESP32-C3 Mini, MPU-6050, ADS1115, GTRIC LR18-08U M18 아날로그 유도형 근접 센서다.
- 실제 보유 GTRIC 센서의 몸체 라벨로 DC 15–30V 동작, 0–10V 출력, 1–8mm 감지 거리를 확인했다. ADS1115에는 분압·입력 보호 회로를 거쳐 연결한다.
- 실물 사진으로 현재 센서 모듈의 배선과 ADS1115용 분압·보호 회로 포함 상태를 확인했다. 사용자는 ESP32-C3 펌웨어 동작, 구동부 출력과 전체 모형 조립 완료를 확인했다. 사진만으로 확인할 수 없는 회로값·측정전압과 미실시 상태인 반복 주행·실측 저장은 완료로 단정하지 않는다.
- ESP32-S3, ADXL345, HC-SR04는 취소된 초기 프로토타입이며 현재 성과로 서술하지 않는다.
- 구동부의 3D 출력 외피 내부에 센서 모듈을 결합하는 물리 구조를 반영한다.
- 원시 센서값은 웨이블릿 디노이징과 파고율 등 특징 공학을 거쳐 AI 모델에 입력된다.
- 합성 데이터와 더미 스트리머는 파이프라인 시연용이며 실제 정확도 증거로 표현하지 않는다.
- 구현 완료, 진행 중, 계획, 검증 필요를 구분한다.
- 첨부 자료에 없는 성능 수치, 시험 결과, 부품 사양, 현장 적용 성과를 추측해서 만들지 않는다.
- 근거가 부족한 필드는 삭제하지 말고 [확인 필요]로 남긴다.
- 과장된 홍보 문구보다 심사위원이 기술 구조와 실제 진척도를 검증할 수 있는 구체적인 문장을 사용한다.
- 팀원 세부목표 표에는 블라인드 평가원칙에 따라 실명을 쓰지 않는다.
- 공식 PDF의 붉은 작성 안내 문구는 최종 이식본에서 제거한다.

먼저 기준 문서 사이의 충돌·오류 목록을 제시한 다음, PDF 1쪽부터 11쪽까지 페이지와 공식 항목별로 이식 가능한 원고를 작성해줘. 본문 문장 외에도 각 표의 셀 내용, 삽입할 사진·구성도 위치와 캡션을 구분해서 제시해줘.
```

## ChatGPT에 사진도 제공할 때

사진을 첨부하고 다음 문장을 추가한다.

```text
첨부 사진은 실제 센서 모듈 부품과 구동부 3D 모델의 증빙 자료다. 사진에서 확실히 식별되는 내용만 설명하고, 보이지 않는 모델명·치수·배선 완성 여부를 추측하지 않는다. Blender 화면의 치수는 선택 지점 간 거리일 수 있으며 과거 7cm 바퀴 기준 화면은 최신 5.3cm 기준과 구분한다.
```

## 권장 작업 순서

1. Cursor에서 통합 문맥과 저장소 구현을 대조한다.
2. 공식 PDF 항목표에 맞춰 항목별 사실 원고를 작성한다.
3. ChatGPT에 공식 PDF, 기준 문서와 초안을 업로드해 문장 구성과 양식 이식을 수행한다.
4. 결과를 다시 Cursor에서 저장소·Notion 근거와 대조한다.
5. `[확인 필요]` 항목을 팀원에게 확인한다.
6. 실제 사진, 회로도, 시험 로그, 모델 학습 결과를 증빙으로 배치한다.
7. 최종 제출 전 현재 하드웨어, 일정, 성능 수치와 라이선스를 다시 검토한다.

## 최종 검수 체크리스트

- 현재 하드웨어와 과거 프로토타입이 혼합되지 않았는가
- 하부 레일 이상이 핵심 대상으로 일관되게 표현됐는가
- 합성 데이터 결과를 실제 정확도로 오해할 문장이 없는가
- 사용자 확인으로 완료된 펌웨어 동작·구동부 출력·전체 모형 조립과 미검증 WSS·반복 시운전·실측 저장을 구분했는가
- 상용 3D 자산 또는 비공개 링크를 보고서나 공개 저장소에 노출하지 않았는가
- 최신 바퀴 지름 5.3cm와 과거 치수 이력이 구분됐는가
- 사진 번호와 본문 설명이 실제 첨부 자료와 일치하는가
- `[확인 필요]` 항목이 팀 확인 없이 임의로 채워지지 않았는가
- 작품 개요와 작품 구성도가 각각 1쪽인가
- 공식 항목명·순서·표 구조를 변경하거나 삭제하지 않았는가
- 팀원 역할 표에서 실명을 제거했는가
- 최종 PDF에서 붉은 작성 안내 문구를 삭제했는가
