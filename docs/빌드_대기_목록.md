# 빌드·배포 대기 목록

코드는 고쳤지만 아직 빌드·설정·확인이 남은 작업을 모은다. 다음에 한꺼번에 빌드할 때 이 목록을 위에서부터 처리하고, 끝난 항목은 지운다.

## 1. 레일 좌표 통일 + 180 cm (브랜치 `claude/rail-coordinate-180cm`)

### 무엇을 고쳤나

- 서버는 레일 길이를 100 cm로 알고 있었고(실물·Unity 모델은 180 cm), 결함 위치 기준점도 두 가지가 섞여 있었다
  - 주행 파형 적합(`pass_analysis.py`)은 레일 왼쪽 끝 기준(예: 600~1200 mm)
  - 구간 규칙(`rail_defect.py`)과 Unity·대시보드 색칠은 엔코더 기준 + 구동바퀴 58 cm
  - 그래서 실측 주행 중에는 결함 색이 실제보다 약 58 cm 뒤(118~158 cm)에 칠해졌다. 실측 CSV 재생 화면은 58 cm를 더하지 않아 맞아 보였다
- 이제 서버의 모든 결함 위치는 **레일 좌표(레일 왼쪽 끝 = 0 mm)**다
  - `rail_defect.py`: 레일 좌표 = 좌 엔코더 + `SENSOR_START_MM`(기본 290). 더미 샘플은 이미 레일 좌표라 더하지 않는다. 파형 적합에는 엔코더 원시값을 그대로 넘긴다
  - `main.py`, `.env.example`, `docker-compose*.yml`: 기본값 `RAIL_LENGTH_CM=180`, `RAIL_SEGMENT_COUNT=36`(구간 50 mm)
  - `frontend/index.html`, `RailTwinController.cs`: 결함 색칠과 결함 목록에서 58 cm 보정을 뺐다. 58 cm는 대차 위치 표시에만 쓴다
- 검증(이 브랜치, 9/28 실측 24회 재생): 판별 18/18 그대로. 세 결함 모두 Unity 색칠 위치가 실제 결함 위치 60~120 cm와 같다

### 빌드할 것

- [ ] **Unity WebGL 다시 빌드** (`RailTwinController.cs`의 `Paint()`가 바뀜). 맥에서:
  ```bash
  UNITY="/Applications/Unity/Hub/Editor/6000.6.0f1/Unity.app/Contents/MacOS/Unity"
  "$UNITY" -batchmode -nographics -quit \
    -projectPath "$(pwd)/unity/RailTwinRails" \
    -executeMethod RailTwinWebGLBuild.Build \
    -logFile unity-webgl-build.log
  bash scripts/sync_unity_webgl.sh   # Build/ → frontend/unity/Build/
  ```
  `frontend/unity/Build/`의 바뀐 파일 4개를 **이 브랜치에 같이 커밋**한다

### 서버 설정 (GitHub로 바뀌지 않음, NCP 서버에서 직접)

- [ ] 서버 `.env`를 아래처럼 고친다. 2026-10 서버 백업의 `.env`에는 `RAIL_LENGTH_CM=100`, `RAIL_SEGMENT_COUNT=20`이 적혀 있어서, 코드 기본값을 바꿔도 그대로 덮어쓴다
  ```
  RAIL_LENGTH_CM=180
  RAIL_SEGMENT_COUNT=36
  SENSOR_START_MM=290
  ```
- [ ] 고친 뒤 FastAPI를 재시작한다. 정상 기준선(`rail_baseline.json`)은 다시 등록하지 않아도 된다. 기준선은 이음부로 맞춘 격자라 이번 좌표 변경과 무관하다

### 배포 순서 (중요)

- [ ] **Unity 빌드 파일이 이 브랜치에 들어간 뒤에만 `main`에 합친다.** 서버·대시보드만 먼저 배포되면, 예전 Unity 빌드가 새 레일 좌표에 58 cm를 또 더해서 Unity 화면만 어긋난다
- [ ] 합치기 전에 맥에서 전체 테스트를 돌린다. 이 브랜치는 클라우드에서 fastapi가 없어 `tests/test_sensor_contract.py`와 실측 재생만 돌렸다
  ```bash
  python3 -m venv .venv && source .venv/bin/activate
  pip install -r requirements.txt pytest
  pytest -q
  python replay_csv.py "배준호_전달/레일측정데이터"   # 판별 18/18 확인
  ```
- [ ] 배포 뒤 대시보드에서 확인: 실측 주행 1회 후 결함 목록 구간이 60~120 cm 근처인지, Unity와 아래 rail_risk 막대가 같은 곳을 칠하는지

### 확인 필요 (하드웨어 문서 받은 뒤)

2026-09-24 하드웨어 인수인계서에는 아래 값이 없다("레일 위 0mm 미확인"). 줄자로 재야 정해진다.

- [ ] `SENSOR_START_MM`(엔코더 0일 때 센서의 레일 좌표) 실측. 엔코더를 0으로 둔 출발 자세에서 **레일 왼쪽 끝 → LR18 센서 중심** 거리를 줄자로 잰다. 지금 두 추정값이 약 45 mm 다르다
  - 9/28 실측 24회에서 이음부 위치로 역산: 중앙값 **289 mm**(254~316 mm). 서버 기본값 290은 이것이다
  - 출발 구동바퀴 접점 580 mm − GLB 모델의 센서·구동바퀴 거리 약 246 mm = **약 334 mm**
  - 실측값이 나오면 서버 `.env`의 `SENSOR_START_MM`만 바꾸면 된다(코드 수정 불필요)
- [ ] 엔코더 배율. 9/28 실측에서 이음부 간격(600 mm)으로 본 배율이 0.84~0.99(중앙값 약 0.89)였다. 엔코더가 실제보다 약 10% 더 센다. 파형 적합은 이음부로 자동 보정하지만, 주행 중 구간 규칙은 보정하지 않아 레일 끝 쪽으로 갈수록 위치가 밀린다(예: 120 cm 이음부가 125 cm 근처로). 아래 2번 동기화를 올린 뒤 다시 잰다

## 2. 펌웨어 좌·우 바퀴 동기화 (같은 브랜치, 0.6.8-draft)

### 무엇을 고쳤나

- 하드웨어 인수인계서(2026-09-24): 같은 PWM에서 좌 모터가 약 13% 빠르다(517 대 455). 동기화 없이 달리면 한쪽이 미끄러져 엔코더 거리가 벌어진다. 브링업은 `syncDrive()`, `SYNC_KP = 2.0`을 썼다
- 그런데 실물용 `firmware/esp32_s3_rail_node/` 0.6.7-draft는 두 모터에 같은 듀티를 넣었다. 9/28 실측의 좌·우 엔코더 차(최대 29%)와 배율 흔들림의 원인으로 본다
- 0.6.8-draft: 주행을 시작한 뒤 좌·우가 간 거리 차(mm) × `SYNC_KP`(2.0)만큼 빠른 쪽 듀티를 빼고 느린 쪽에 더한다. 상한은 60, 그리고 기본 듀티의 절반. 멈추거나 방향을 바꾸거나 위치를 0으로 하면 기준을 새로 잡는다. `config.h`의 `SYNC_ENABLED = false`로 끌 수 있다
- 시리얼 `r` 줄 끝에 `동기화 +n`(지금 보정 듀티)을 찍는다
- 단순 모터 모델 계산(좌 13% 빠름, 25초): 좌·우 차가 평속 161 mm → 5 mm, 감속 54 mm → 2 mm. 바퀴 미끄러짐은 넣지 않은 모델이라 실물 시험이 필요하다

### 빌드·업로드할 것

- [ ] **컴파일 확인.** 클라우드에 arduino-cli가 없어 컴파일하지 못했다. 맥에서 먼저 컴파일만 해 본다. 보드 ESP32S3 Dev Module, USB CDC On Boot: Enabled
  ```bash
  arduino-cli compile --fqbn esp32:esp32:esp32s3:CDCOnBoot=cdc firmware/esp32_s3_rail_node
  ```
- [ ] 업로드 (네이티브 USB 포트, `arduino-cli board list`로 포트 확인)
  ```bash
  arduino-cli upload -p <포트> --fqbn esp32:esp32:esp32s3:CDCOnBoot=cdc firmware/esp32_s3_rail_node
  ```

### 시험

- [ ] 시리얼 시작 줄이 `0.6.8-draft`인지 확인
- [ ] 레일 위에서 `g`(평속)로 달리며 `r`을 몇 번 찍는다. 좌·우 위치 차가 수 mm 안에 머무는지, `동기화` 값이 + 쪽(좌가 빠름)으로 작게 붙는지 본다
- [ ] 바퀴가 좌우로 흔들리거나(보정이 너무 셈) 차가 계속 벌어지면(너무 약함) `SYNC_KP`를 1.0 또는 3.0으로 바꿔 다시 본다
- [ ] BOOT 25초 주행 1회 뒤 **줄자 이동 거리**와 좌 엔코더 거리를 비교한다. 차이가 10% 가까이 남으면 바퀴 지름을 재서 `MM_PER_COUNT`를 고친다
- [ ] 동기화 펌웨어로 정상 레일을 3회 이상 달려 정상 기준선을 **다시 등록**한다(대시보드 기준선 모드). 주행 방식이 바뀌어 9/28 기준선과 파형이 달라질 수 있다

### 2026-09-25에 이미 확정된 것 (다시 볼 필요 없음)

- 코드의 좌(`Wire`, GPIO11/12, `rail-left-01`) = 실물 왼쪽. 전진 = 빨간 모터 기판 쪽
- GY-521 두 장 모두 Z 위, 인쇄된 +X가 차체 왼쪽. 서버 기울기 계산의 축 가정과 같다
